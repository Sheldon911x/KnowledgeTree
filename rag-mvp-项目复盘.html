一、这是什么（30 秒版）

不用任何 RAG 框架，用 Python + Ollama 本地模型手写 RAG 五个环节，配三种检索模式对比和黄金集自动评测。目的是搞懂 RAG 的工程全貌，而不是调 API。

角色选型说明
嵌入模型bge-m3（Ollama）文本 → 向量，支持批量接口
生成模型qwen2.5:3b（Ollama）基于检索到的块作答
向量库numpy 余弦相似度 + JSON 落盘无外部服务，vector_store.json（约 4MB）
检索dense / bm25 / hybrid 三种模式BM25 为纯 Python 手写实现，零额外依赖
依赖numpy + requests（+ openpyxl 读 Excel；pypdf / python-docx 可选）

五、学习复盘：这次真正学到的 5 件事

  1. RAG 的瓶颈在检索，不在生成。评测脚本只测检索层（Recall@K），不调生成模型——因为"找对了块，答案自然对；找错块，生成再强也是脑补"。这也解释了为什么"库外问题脑补"是已知短板。
  2. 中文场景混合检索是底线，不是加分项。改写问题下 BM25 召回只有 0.5。纯关键词检索在中文 paraphrase 面前很脆，必须靠向量兜底。
  3. "感觉还行"不值钱，黄金集 + 指标才值钱。8 条改写问题 + Recall@K，把调参从玄学变成实验：改配置 → 重 build → 重测 → 比数字。这套闭环可以原样搬进工作里的 RAG 方案评估。
  4. 切块策略必须匹配数据形态。xlsx 问答集按"一行=一块"，绝不被字符窗口切断；普通文档才走 600 字滑窗。一刀切的切块是检索质量的头号隐形杀手。
  5. 把所有开关集中到配置区，是可实验性的前提。改一行参数就能做一组对照实验；如果参数散落在代码各处，对比实验根本做不起来。
