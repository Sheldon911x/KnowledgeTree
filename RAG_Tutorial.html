② 写入路径：数据怎么"入库"

RAG 的质量上限由索引质量决定。没有好的数据准备，再强的检索也白搭。

W1 文档解析

📄 多格式文档→结构化文本

将 PDF、Word、Markdown、HTML、PPT 等异构文档统一解析为纯文本+表格+图片描述。关键挑战：PDF 排版还原、表格提取、OCR 识别。

点击查看工具选型 →

W2 智能分块

✂️ 把文档切成合适的"片"

分块大小直接影响检索精度：太大丢失精度，太小丢失上下文。常用策略：固定窗口(512 token)、语义分块(按段落/标题)、递归分块。

点击查看分块策略对比 →

W3 向量嵌入

🧮 文本 → 数字向量

将文本块通过 Embedding 模型转为高维向量（如1024维），语义相似的文本向量距离近。中文推荐：BGE-large-zh、m3e-base、text2vec-large-chinese。

点击查看模型推荐 →

W4 索引构建

🗂️ 建立"字典"：向量索引+关键词索引

向量索引（HNSW/IVF）用于语义搜索；BM25 倒排索引用于关键词搜索。常见向量库：Chroma(入门)、FAISS(高性能)、Milvus(生产级)。

③ 查询路径：一条请求的 8 步旅程

从用户输入到带来源的答案，每一步都在提升答案质量

R1

用户提问

起点。可前置意图识别：判断问题是否需要知识库检索，闲聊直接走 LLM。

R2

Query 改写

将口语化问题转为检索友好表达：同义词扩展、多子查询生成、假想文档(HyDE)。「怎么打这个游戏」→「游戏通关攻略 技巧」

R3

混合检索：向量+BM25

双路召回，取长补短：向量擅长语义相似（"开心"≈"高兴"），BM25 擅长精确匹配（产品名、编号、日期）。

R4

RRF 融合

两路检索结果分数不可比？不用分数，用排名！RRF 核心公式：score = Σ 1/(k+rank)，k 常取 60。

R5

Cross-Encoder 精排

"粗筛"之后"精选"：用更强的模型对 Top-20 重新评分，取 Top-5。比双编码器慢 100 倍，但准确度大幅提升。

R6

上下文组装

父子块扩展+去重+压缩到 8000 token 以内。小块检索精准，大块回补上下文。对表格做结构化还原。

R7

LLM 生成+自检

基于检索内容流式生成回答，附带自检纠错(CRAG)：评估生成内容是否被检索结果支撑，不支持的重新检索或标注不确定。

R8

来源标注

关键环节！回答引用粒度：文档级→段落级→句子级。常用做法：将文本块 ID 注入 Prompt，让 LLM 输出引用编号。

④ 核心概念深度讲解

每个概念都拆解为：是什么 — 为什么 — 怎么做 — 入门 vs 进阶

深度

Query 改写技术

不止是同义词扩展。HyDE（用 LLM 生成假想答案再检索）、Multi-Query（拆成多个子问题分别检索）、Step-Back（先抽象再检索）。

深度

混合检索原理

为什么向量+BM25 是黄金组合？稀疏 vs 稠密表示的数学直觉、各自的优势场景、Elasticsearch 和 Milvus 的双路实现。

深度

RRF 融合算法

为什么不用归一化分数？RRF 的数学原理、k 值调优、与其他融合方法（加权求和、CombSUM/CombMNZ）的对比。

深度

Cross-Encoder vs Bi-Encoder

双编码器（检索）和交叉编码器（精排）的本质区别：独立编码 vs 联合编码。BGE-Reranker、Cohere Rerank 使用指南。

深度

父子块与表格处理

Small-to-Big 策略：小粒度检索（→精准），大粒度返回（→完整上下文）。表格需要特殊处理：结构识别+行列关系保留。

深度

上下文压缩策略

去重→冗余过滤→LLM 摘要压缩(LLMLingua)。8000 token 是如何得出的？不同模型的窗口差异与自适应策略。

安全护栏设计

输入层：Prompt Injection 检测、敏感词过滤。输出层：幻觉检测、PII 脱敏、越界拒绝。与 Prompt 模板的协同设计。

自检纠错(Self-RAG/CRAG)

⑥ 三套落地方案（固定搭配）

不用纠结选型：下面三套是「开箱即用」的固定组合，覆盖从零成本到生产级。先选预算和机器，再照单配置。

方案 A — 入门零成本（纯本地 CPU）

目标：不花一分钱，用现有笔记本跑通一个 RAG Demo

🧩 固定技术栈
  • 框架：LlamaIndex
  • 向量库：Chroma（本地文件）
  • 嵌入模型：BGE-small-zh-v1.5（512维，轻量）
  • 生成模型：Qwen2.5-3B-Instruct（本地 Ollama 跑）
  • 检索：纯向量 + 固定分块 512 token
💰 成本
  • 软件/API：¥0
  • 硬件：使用现有电脑
  • 电费：可忽略
  • 模型下载：约 1.5 GB（一次性）
🖥️ 设备配置要求
  • CPU：4 核以上（Intel i5 / R5 起）
  • 内存：≥ 8 GB（建议 16 GB）
  • 硬盘：≥ 5 GB 空闲（模型+索引）
  • GPU：不需要
  • 耗时：首次索引约 1-2 分钟/百篇
# 一键安装 pip install llama-index chromadb ollama ollama pull qwen2.5:3b # 跑通（约 20 行代码） from llama_index.core import VectorStoreIndex, SimpleDirectoryReader, Settings from llama_index.embeddings.huggingface import HuggingFaceEmbedding Settings.embed_model = HuggingFaceEmbedding("BAAI/bge-small-zh-v1.5") Settings.llm = Ollama(model="qwen2.5:3b") # 本地生成，零成本 docs = SimpleDirectoryReader("./docs").load_data() index = VectorStoreIndex.from_documents(docs) print(index.as_query_engine().query("你的问题"))

⑧ 术语速查表

RAG 世界的黑话，一次查清楚

🧱 基础概念（What）

RAG（Retrieval-Augmented Generation）
检索增强生成：先检索相关知识，再让 LLM 基于这些知识生成回答，减少幻觉。
Chunking（分块）
将长文档切成小段的过程，直接影响检索精度。块太大丢精度，块太小丢上下文。
HyDE（Hypothetical Document Embeddings）
假设性文档嵌入：先让 LLM 生成一个假想答案，再用这个答案去检索（而非原始问题）。

🔢 向量与编码（Embedding Family）

Embedding（嵌入/向量化）
将文本转为高维数字向量，语义相近的文本向量距离也近。
Bi-Encoder（双编码器）
Query 和 Document 分别独立编码，速度快，适合大规模检索（粗排）。
Cross-Encoder（交叉编码器）
Query 和 Document 拼接后一起编码，精度高但慢，适合精排（Re-rank）。

🔍 检索与排序（Retrieval Family）

BM25
经典关键词检索算法，基于词频和逆文档频率，擅长精确匹配（产品编号、人名、日期）。
RRF（Reciprocal Rank Fusion）
倒数秩融合：通过排名（而非分数）融合多路检索结果的无监督算法，公式 Σ 1/(k+rank)，k 常取 60。
HNSW
分层可导航小世界图，最常用的近似最近邻（ANN）向量检索算法之一。

🛡️ 质量与治理（Quality & Ops）

CRAG / Self-RAG
生成后自检：评估回答是否被检索内容支持，不达标则修正或重新检索（Corrective / Self-Reflective RAG）。
RAGAS
RAG 评估框架，衡量检索召回率（Faithfulness）、答案相关性（Answer Relevancy）等指标。
LLMLingua
微软的 Prompt 压缩工具，用小型 LLM 精简上下文，减少 Token 消耗。

⚠️ 关键遗漏（必须补）

写入路径

① 数据接入与索引构建（离线）

你的 11 步只描述了「查询路径」。但 RAG 的质量上限由索引决定：文档解析→分块→嵌入→索引。没有这一半，检索无的放矢。教程 ② 写入路径 + ③ 查询路径已补全。

评估闭环

② 评测体系（RAGAS / TruLens）

没有评估就无法迭代。需量化：检索召回率、答案忠实度、相关性。教程 ⑥ 方案B 已引入 RAGAS。

缓存与可观测

③ 语义缓存 + 全链路 Trace

相似问题命中缓存可省成本；Langfuse/LangSmith 追踪每一步质量。工程化必备，教程 ⑥ 方案C 已覆盖。

💡 可选增强（非必需）

  • 多模态 RAG：图片/图表检索，需多模态 Embedding（如 CLIP）。
  • GraphRAG：把知识建图，适合复杂关系问答（微软出品）。
  • Agentic RAG：动态选工具/路由（即你的第 3 步），适合多源异构知识。
